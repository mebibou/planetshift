# The app

A static site: Vite, TypeScript and D3, no framework and no backend. It loads the JSON files described in `data-contract.md`, runs the model in the browser on every change, and draws the result.

## Running it

```sh
cd app
npm ci
npm run dev        # development server
npm run build      # type-check and build into app/dist
npm run preview    # serve the build
npm run precompress  # write .gz and .br beside each text file of app/dist, for a host that serves pre-compressed files (GitHub Pages compresses on the fly, so the CI workflow skips this)
npm run lint       # eslint, prettier, tsc
npm test           # Vitest: the model, the lever modules, the goldens and the interface's pure helpers, then the timing tests alone
npm run golden     # record the golden results anew, after a change meant to move them
npx playwright test  # end-to-end, desktop and phone, on the built site
```

Add `?data=fixtures` to the URL to run on the small fixtures in `app/public/fixtures/` instead of the real data in `app/public/data/`; the end-to-end tests always do, so their results do not move when the data is rebuilt.

## Structure

| `src/map/` | The map card (`mapCard.ts`) with its two views, the choropleth (`choropleth.ts`) and the table (`tableView.ts`), and their pure parts: layer values, colour thresholds, legend bins, tooltip rows, intensity sources, and the table's rows, sorting, search and pages (`table.ts`). |

| `test/e2e/` | Playwright tests of the built site. |

## State and the URL

The state is the model's `Scenario` and `Options`, the interface's choices (view, map layer, food group, gas), the language and the theme. Every change goes through one store; the shell then updates the controls (`sync`), re-runs the model once per animation frame or, for an interface choice alone, draws again with the last result (`show`, so the map and the table are drawn once per change), and rewrites the URL. A language switch builds the header and the views anew, after stopping the old header's height tracking and the old Explore's pending worth runs. The model's part of the URL is written by `encodeState` and read by `decodeState` (`src/model/state.ts`): the diet shift under `shift`, the per-group shifts under `rum`, `pig`, `pou`, `dai`, `egg` and `sea`, `basis`, `with`, `where` and `ramp` (a year before the slider's first, the year after the current one, is read as that year); each lever's adoption as a percentage under the key its module declares (`fa` feed additives, `bf` breeding and feed, `mm` manure, `rw` rice water, `ne` nitrogen efficiency, `ni` inhibitors, `fe` farm energy, `fw` food waste, `sl` supply losses, `df` deforestation, `cc` cover crops, `af` agroforestry, `bc` biochar, `ew` rock dust, `ev` electric cars, `et` electric trucks, `fl` less flying, `saf` clean aviation fuel, `cs` clean shipping, `re` renewable electricity, `cdc` data centres on clean power), left out at 0 and read as 0 when invalid; then each option under its key (`scope`, `feed`, `base`, `loc`, `temp`, `clim`, `ssp`, and the modules' `pop`, `regrow`, `dc` and `pf`), left out at its default. The interface adds `view` (`explore`, `methodology`), `layer` (`production`, `emissions`, `land`, `deforestation`, `change`, `quality`), `change` (`production`, `emissions`, `land`), `group`, `gas`, `chart` (`temperature`, `avoided`, `cause`), `to`, `mapview` (`map`, `table`), `range` (`full`, `recent`: the charts' start year) and `causegas` (`all`, `co2`, `ch4`, `n2o`: the gas of the Causes of warming chart) when they differ from their defaults (`src/app/url.ts`) and keeps `data=`. The link view was folded into Explore's charts: an old `?view=link` opens Explore on the Causes of warming tab, and the URL is rewritten to `?chart=cause`. A shared link therefore reopens the same controls, options and view. A link to a Methodology section, such as `?view=methodology#method-climate`, opens on that section's heading, below the sticky header; going back or forward between sections changes only the hash, and the shell ignores a `popstate` whose query is unchanged, so the model does not run again. The language and the theme are kept in `localStorage` instead, as they belong to the reader rather than to the controls.

## Colours and themes

Every colour is a custom property in `src/styles.css`, defined for the light theme on `:root` and again for the dark theme (under `prefers-color-scheme: dark` and under `[data-theme='dark']`, which the toggle sets). Charts and the map use them through CSS classes or `var(--…)` fills, so a theme change needs no redraw. The map's scales are single-hue sequential ramps (green for production, orange for emissions, brown for farmland, red-purple for deforestation, purple for data quality, ColorBrewer-based) and a blue–grey–red diverging scale for change. In both themes darker means more, and a larger change is a deeper colour: the dark theme's ramps run from light to deep like the light theme's, made in OKLCH with even steps of lightness, the deepest step stopping short of the page's background so the largest values still stand out; the chart series and the causes (fossil fuels and industry blue, farming aqua, land use orange, other human emissions violet, natural factors pink, air pollution yellow, in that stacking order) pass the colour-blindness checks of the dataviz palette validator for neighbouring bands, in both themes; the summary's breakdown uses the same cause colours.

## Adding things

**A text.** Add the key to both `src/i18n/en.json` and `fr.json` with the same placeholders (`{name}`), then call `t('the.key', { name })`. `test/ui/i18n.test.ts` fails when the two files differ.

**A lever.** See "Lever modules" below: a lever is a module, or a line in an existing module's `levers`.

**An option.** A core option goes in `Options` in `src/model/api.ts` and `CORE_OPTIONS` in `src/model/options.ts`, with `options.<field>.label`, `.hint` and one text per value in both dictionaries. An option that belongs to a lever module goes in that module's `options` (see below). The end-to-end test reads its list of options from the top of `test/e2e/app.spec.ts`; add it there too.

**A map layer.** Add it to `LAYERS` in `src/map/layers.ts` with its value in `layerValue` (and to `CHANGE_OF` if the Change layer should offer it), its colours in `src/map/colours.ts`, and `map.layers.<id>` and `map.notes.<id>` to the dictionaries.

**A view.** Add it to `VIEWS` in `src/app/url.ts`, build it in `showView` in `src/app/shell.ts`, and add `nav.<id>` to the dictionaries.

**A chart tab.** Add it to `CHARTS` in `src/app/url.ts`, its panel in `src/app/explore.ts` (`panels` and `drawCharts`), and `charts.tabs.<id>` to the dictionaries.

**A methodology section.** Write `docs/methodology/en/<id>.md` (and `fr/<id>.md` when translated; the English one is shown until then), and add the id to `HEAD` or `TAIL` in `src/methodology/sections.ts` where it belongs, or, for a lever module's page, name it in the module's `methodology`. A section listed without a file is skipped; a file not listed is not shown.

## Lever modules

Each lever, or each family of levers that share all their code, is a folder in `src/levers/<id>/`, so that work on one lever touches only its folder and one line of `src/levers/registry.ts`. The diet shift (main slider, per-group sliders, basis, replacement, where, ramp) stays in the core: every other part of the model builds on it, and making it a module would only move code.

A module's folder holds:

- `index.ts`: the module (`LeverModule` in `src/levers/types.ts`): its `id`, the `departure` from FaIR it is, if any (see "Forking"), the `family` its effect is counted in (none for a feedback such as permafrost), whether that family is farming (`farm`), the `cause` of warming it mainly acts on (`fossilIndustry`, `agriculture` or `landUse`: its group's heading in the panel, and the cause its own country CO₂, world emissions and warming count in; farm emissions always count in farming), its `levers` (each made with `lever(module, id, urlKey)`: a 0–100% slider, default 0, texts at `levers.<module>.<lever>.title` and `.description`), its `options` (made with `option(module, field, urlKey, values)`, the default first, drawn in the Options group), the data `files` it reads with what stands for each when the build has none (and `deferred: true` for a large file loaded only once one of its levers is above 0, its levers showing at once and acting when it arrives), `available` (whether the data has what a lever needs), its `hooks`, its `ui` (`section: 'levers'` for a fold in the Levers section; `stat` for a figure in the summary strip) and its `methodology` (`{ page }` for its own page, or `{ coveredBy }` naming the core page that explains it).
- `data.ts` when it reads a file of its own: the file's type, its empty value, and a `declare module` that adds the file to `ModelData`; the same `declare module` adds the module's options to `Options` and its own fields to `CountryResult` and `Summary`.
- `model.ts`: its pure functions.
- `en.json` and `fr.json`: its texts, merged into the dictionaries under `levers.<id>`: `title` and `description` of its fold, `family` (its name in the breakdown), `page` (its Methodology page's fallback title), one entry per lever, `options.<field>` and `summary.*` for its figure.
- Its tests (`<id>.test.ts`), using the helpers in `test/levers.ts`.

The core run (`src/model/run.ts`) calls the hooks at fixed points, each optional, each given the run's context (`RunContext`: the prepared data, scenario, options, current year and `adoption(id)`) and returning null when the module has nothing to do:

| Hook | Called | Returns |
| --- | --- | --- |
| `population` | before the baseline, once per options | the world population by year to use in place of the countries' own (another projection, the population module); the population baseline scales farm emissions by it, in the baseline temperature and in the run alike. The first module that returns one is used |
| `demand` | after the diet shift | what people use once the diet has shifted (less food wasted), per country |
| `supplyChain` | with `demand` | the supply each tonne of use needs and the losses avoided; a module with either is a production step, run on top of the diet and the steps before it, and its family gets the difference in farm emissions |
| `intensity` | per country and band | the share of each item's intensity of each gas removed, applied to the production with every step (farm practices) |
| `country` | per country, after production and land | CO₂ a year by family (a constant stream, such as clearing following each step) and its own fields of the country's result |
| `world` | once, with every country's result | `extraEmissions` (its family's emissions each year by band, such as uptake or fossil CO₂), `extraWarming` (warming from forcing that is not an emission, such as contrails), `warmingByCause` (warming it counts in a cause other than its own: the energy and industry levers' air pollution, under `airPollution`), its fields of the summary and its own fields of the result (`result`, such as the population chart's series), declared on `ScenarioResult` with `declare module` |
| `baseline` | in registry order, on the baseline temperature so far | warming it adds to the baseline (data centres, the 2020 shipping rule, the permafrost release) and what it keeps for `feedback` |
| `feedback` | after every family's change in temperature | the warming that change causes in turn (permafrost), shared out between the families, and between the causes, in proportion to the size of their warming |

`src/levers/registry.ts` lists the modules in `MODULES`, whose order fixes the order of the modules' options after the core's (population first, after the scenario world) but not the breakdown, which is the same in any order; `PANEL_ORDER` gives the order of the levers in the URL and of the modules' Methodology pages (the panel orders its groups by cause and worth), and `SUMMARY_ORDER` that of their figures in the summary strip (a module left out of either comes after those listed, in registry order). Everything the core needs is derived from it: `LEVERS`, `FAMILIES`, `FARM_FAMILIES`, `LEVER_CAUSES` (the panel's headings), `COUNTED_CAUSES` (the causes a result is split into: those and air pollution), `DIET_CAUSE`, `causeOfFamily`, `MODULE_OPTIONS`, `LEVER_FILES`, `MODULE_PAGES`, `adoptionOf`, `leverAvailable` and `familyLabel`. The core files (`run.ts`, `state.ts`, the panels, the summary, the map, `load.ts`) loop over these and name no lever.

To add a lever:

1. Make `src/levers/<id>/` with `index.ts`, and `data.ts`, `model.ts` as needed, starting from the module closest to it.
2. Write its texts in `en.json` and `fr.json` with the same keys and placeholders.
3. Write its Methodology page in `docs/methodology/en/<page>.md` and `fr/<page>.md`, or name the core page that covers it.
4. If it reads a new data file, add its section to the pipeline (`pipeline/README.md`) and its fixture to `scripts/gen-fixtures.mjs` (`npm run fixtures`).
5. Add one line to `MODULES` in `src/levers/registry.ts` where its family counts, and to `PANEL_ORDER` if its fold should not come last.
6. Write its tests beside it; `src/levers/contract.test.ts` checks every module without being told: unique ids and URL keys, no effect at 0 or at an option's default, the URL round-trip with invalid values, both languages with the same placeholders, more adoption avoiding at least as much warming (on the fixtures and the real data), a Methodology page in both languages and a fixture for each file; `test/model/timing.test.ts` times a run with everything on, and `test/model/attribution.test.ts` checks the breakdown against the Shapley values of full runs. A module whose family interacts with another farm family other than through production (the diet and less waste) breaks the breakdown's shortcut, and that test then fails.
7. Run `npm test`: the goldens in `test/golden/` must not move, as a new lever at 0 changes nothing; add its id to the grid in `test/golden/grid.ts` and run `npm run golden` to record its own results.

## Forking

`planetshift.config.json` at the repository's root holds a fork's departures from FaIR's own physics, each a named switch; `planetshift.config.schema.json` lists them, each with its values, its `default` (the website's) and its `plainFair` value (the one that keeps to FaIR). A switch left out takes its default; an unknown key or value stops the build. The pipeline checks it (`planetshift_pipeline/config.py`), logs it and writes it into `meta.json` (`departures`), and writes the data every value needs, so the same data serves any config. The app reads it when it is built: `vite.config.ts` checks it with `resolveDepartures` (`src/configSchema.ts`) and defines `__PLANETSHIFT_DEPARTURES__`, which `src/config.ts` exports as `DEPARTURES`. Visitors never see the switches: they are not `Options`, not in the Options group and not in the URL.

A run reads them with `departuresOf(data)`: `data.departures` when set (the tests set it, to run with every switch at its plain-FaIR value), else the build's. A switch that is a module of its own (`permafrost`, `shippingSulphur2020`) is named in the module's `departure`: with it `off` the registry leaves the module out of the build, its option with it, and its hooks also check `departs(data, …)`. The other switches pick between variants the data holds. `test/golden/real-plain.json` and `fixtures-plain.json` record a grid of runs with every switch at its plain-FaIR value.

| Switch | Values (default first) | Plain FaIR | Where |
| --- | --- | --- | --- |
| `noxMethane` | `chemistry`, `fair`, `hoor` | `fair` | the methane a kg less NOx leaves: the chemistry models' own value on land and at sea (Hoor et al. 2009), carried by FaIR's change with the scenario, FaIR's one coefficient, or FaIR's coefficient shared between land and sea by Hoor et al.'s ratio, keeping its world total. `coemissions.json`'s `noxCh4PerKgCo2` and `noxPlaceFactor` hold each variant (`coemissions.py`, `nox_factors`); `noxMethane` in `src/levers/energy/coemissions.ts` reads the one picked |
| `aviationNonCo2` | `lee2021`, `fair` | `fair` | what less flying cuts besides CO₂: Lee et al. (2021)'s non-CO₂ forcing (`sectors.json`'s `aviationNonCo2`), or aviation's own NOx, SO₂ and soot as the co-emissions of `aviationOwn` in `coemissions.json`, FaIR having no contrails (`aviationCo` in `src/levers/energy/model.ts`) |
| `permafrost` | `on`, `off` | `off` | the permafrost module and its visitor option (`pf`, off for visitors by default); its constants are in `climate.json` |
| `shippingSulphur2020` | `on`, `off` | `off` | the `shippingSulphur` module: the IMO's 2020 fuel sulphur limit as a forcing outside FaIR's ensemble (`climate.json`'s `shippingSulphur2020`, by SSP), through `sectors.json`'s forcing response, added to the baseline |

Not departures, as they are inputs rather than FaIR's physics: the visitor options (the AR6 curves, the SSP, the data centres' growth, the population projection), the scenario data and inventories, the co-emission ratios' trends, the grid intensity stopped at zero and the linear response around the scenario.

To add a departure: add the switch to the schema with its values, `default`, `plainFair` and `description`, and to `planetshift.config.json`; add its field to `Departures` in `src/configSchema.ts`; write the data each value needs in the pipeline; read it with `departuresOf(data)` where the model uses it, or, for a module of its own, set the module's `departure`; and record the goldens anew (`npm run golden`), the plain-FaIR ones included.

## The Explore page

**The layout.** The page holds four blocks in this order: the chart card, the panel, the summary and the food and farming map. On a phone they stack in that order, so the chart opens the page and the controls follow it. From 861 px the panel moves to a sticky left column beside the others (`grid-template-areas` in `.explore`), and from 1,400 px the summary takes a sticky right column. The order is set in the markup rather than with CSS `order`, so the keyboard and screen readers meet the blocks in the order they are read.

**The panel** starts with the two time settings: *All levers fully in place by*, the year every lever, the diet included, is reached in full (`rampEnd`, under `ramp` in the URL), and *Results up to*, the horizon, 2050 or 2100 (`to` in the URL), which sets the charts' last year, the warming each cause and lever group shows, the order of the groups and the summary strip, so it is a setting of the whole page rather than of the chart card. Then come the lever groups, each a native `details` element (keyboard and screen readers open and close it), closed at first, whose summary gives its title, one line of what is set and what it is worth, under a small "Levers" heading and a heading per cause of warming, with the warming that cause causes by the horizon:

- **Fossil fuels and industry**: Energy and transport, Buildings and industry. **Farming**: Diet (the main shift, kept equal, replaced by, where, and "Shift each animal food" folded inside it; its line says "No shift yet" or "40% moved", and "some foods set apart" when a food has its own share), Farm practices, Food waste. **Land use**: Deforestation, Carbon in farmland. Each lever group holds its description, its levers' sliders and "adopt all in full" / "reset"; its line says "2 of 7 adopted" or "None of 7 adopted".
- The causes are ordered by the warming each causes by the horizon under the scenario world (`climate.attribution`), and the groups within a cause by what each is worth (below), larger first (`panelOrder` in `src/app/panelOrder.ts`). The order is worked out once every group's figure is known for the current options, horizon and data, and kept until one of them changes (`orderKey`): a slider, the timing one included, never reorders the panel, and the groups are moved only when the order differs, so a focused control keeps its focus.
- **Quick 0% / 100% pairs** set a whole group, cause or the panel at once, with the group left open or closed as it was: one beside each group's summary, one on each cause heading for every group under it, and one beside the Levers heading, "All", for every group. They are buttons beside the summary, not in it, as interactive content in a `summary` would toggle the group and confuse screen readers; each has its accessible name ("Set Energy and transport to 0%", "Set every lever under Farming to 100%", "Set all levers to 0%"). The button matching where its groups stand is pressed (`aria-pressed`): 0% when every lever is at 0, 100% when every lever is in full, neither in between. For the Diet, 0% and 100% set the main shift and clear the foods set apart under "Shift each animal food", so 100% moves every animal food in full and 0% none, as "all levers at 0%" promises; keeping a food's own share would leave the pair showing neither state right after a click. A click is one change of the scenario (`withGroupsAt` in `src/controls/adoption.ts`), so the model runs once and the URL is written once, and it never reorders the panel. Other options have no pair: they are not levers.
- **Other options**, last and closed: the core options and every module's options (AI data centres, permafrost, freed farmland), which change the baseline or apply across groups rather than belong to one; its line says "All at their defaults" or how many are changed.

**What each lever is worth.** Beside the diet, each family, each animal food and each lever, a figure such as −0.02 °C gives the change in warming at the chart's horizon (2050 or 2100) if that alone were adopted in full, from no shift and no lever, with the current options, ramp year and the diet's basis, replacement and where. "Alone" was chosen over "on top of the current settings": the figure does not move while other sliders do, it reads as a ranking of where the big levers are, and it needs one run per figure rather than one per figure after every move. A bar behind each figure shows it against the largest of its kind (headers against headers, foods and levers against each other); a figure that adds warming is signed + and coloured as a warning. `src/app/worth.ts` lists the 33 runs (`worthJobs`), keys each by its scenario and options (`jobKey`, so a run is never repeated while its inputs are the same), and runs them one per idle callback after 400 ms without a change, so slider moves never wait for them. They run on the data as loaded so far, and the first of them asks for every deferred lever file (`ViewContext.loadAll`): without the practices' `breakdown.json` the practices would be worth nothing and misplaced in the panel. The file stays out of the first load; once it arrives the figures are computed again and the panel reordered. The run-time budgets are in `test/model/timing.test.ts`.

**The guided start** (`src/app/tour.ts`, its styles in `tour.css` beside it) opens over Explore on a first visit: a modal `dialog` of three steps, what the chart shows, how the levers work and where the causes are, with Back, Next (Start exploring on the last) and Skip. The native modal keeps the focus inside, Escape closes it, and the focus starts on Next and stays on the buttons; each step's progress, title and text are in a polite live region, which the dialog's description also points to. Closing it in any way stores `planetshift.tour` in `localStorage`, read and written in `try`, so it does not open again in that browser; when storage throws, it opens again on the next visit. `main.ts` decides before the app starts, as the shell rewrites the URL: `?tour=1` opens it whatever is stored, `?tour=0` keeps it closed, and neither is kept in the URL. It opens in the page's language and only on Explore. The end-to-end tests store it as seen before every test but the two tagged `@tour`.

**The chart card** has three tabs, Global temperature, Warming avoided and Causes of warming (the tab pattern, like the map's: the arrow keys, Home and End move between them, `tabKeys` in `src/app/tabs.ts`), with, for temperature and by cause, the start year (1850 or 2000). The temperature chart's lines are "Without the levers" and "With the levers"; it shows totals only, with no cause singled out, as no cause is preferred over another, and a "See what causes the warming" link under it opens the Causes of warming tab (`chart=cause`), as the tab does. Causes of warming is what The link page used to show: the headline (the warming so far), what each cause adds or takes away, the sentence on what the levers avoid of each cause, warming by cause stacked, and why the gases are kept apart, folded. A switch over the stacked chart, *All gases*, *CO₂*, *Methane* and *N₂O* (`causegas` in the URL), picks what it stacks. Under *All gases* it has six causes (fossil fuels and industry, farming, land use, other human emissions, natural factors, air pollution below zero; a build without `airPollution` and `natural` shows the four it has) and the temperature measured over them. A gas shows that gas's warming by the causes that emit it, from `climate.attributionByGas` (land use only for CO₂), with *Other sources and interactions* for the rest of the gas, and no measured temperature, which no single gas adds up to; air pollution and the natural factors appear under *All gases* only. A build without `attributionByGas` hides the switch and shows *All gases*. The legend is ordered by the size of each cause at the horizon. After today each lever cause's band is the attribution's median less what the levers avoid of it (`temperature.avoidedByCause`, or `temperature.avoidedByGas` for a gas), and the bands without the levers are drawn as faint dashed outlines; the hover gives each cause with and without the levers. Its Methodology page (`link.md`) stays. The temperature chart has an empty `.chart-slot` under it (`TemperatureChart.slot`) for a small chart such as population.

**Temperature milestones** (`src/app/milestones.ts`; research in the plan, §13.2): the temperature chart draws the Paris Agreement's 1.5 °C ("pursue efforts to limit") and 2 °C ("stay well below") as dashed lines with a short label, the full wording in their tooltip and in the caption, and no 1.8 °C line. Dots mark the year the baseline's and the scenario's medians cross each line; on a phone the years are left to the summary. With the horizon at 2100, a small band in the right margin shows where current policies lead, 2.7–2.8 °C (Climate Action Tracker, November 2026; UNEP Emissions Gap Report 2026). The caption says that warming levels are 20-year averages and a single year above a line does not cross it. A crossing year is the first year the 20-year centred mean (shorter at the ends of the series) reaches the level; its likely range is the years the 5–95% band's warm and cool edges reach it ("likely from 2042" when the cool edge never does). The summary's "Paris Agreement levels" lists, for each level, the year it is reached without and with the shift (or "not before 2100"), the share of the gap to each level the shift closes in 2100, (baseline − scenario) ÷ (baseline − level), and the scenario's peak warming before 2100, or that it is still rising then.

**Natural factors only.** When `climate.json` has `naturalOnly`, the temperature chart draws its median as a thin line, "Natural factors only (sun and volcanoes)", with a legend entry and a row in the hover; without it the line and the entry are hidden. The fixtures have one (a flat line with dips after large eruptions) so the interface can be tested.

**El Niño and La Niña years.** When `enso.json` is there, the observed line has a small dot on each El Niño year (red) and La Niña year (blue), with a legend entry, "El Niño and La Niña years", and a row in the hover giving the year's phase and its annual ONI; neutral years have none. The dots are picked by `ensoMarks` (`src/chart/series.ts`), their colours are `--enso-elNino` and `--enso-laNina` in both themes. Without the file the dots and the entry are hidden. The milestone caption says why the Paris levels are 20-year averages: single years swing about ±0.2 °C around the trend with El Niño and La Niña. The fixtures have an index swinging every 4.3 years.

**Tooltips.** A chart's hover shows a crosshair and the values of the nearest year; the map's shows the country under the pointer, and a click or tap pins it (its source link can then be followed) until a tap on the sea or outside the map, or Escape. On a touch screen a tap pins the map's tooltip only when the finger did not move, so a scroll that starts over the map shows nothing, and a chart keeps its tooltip once the finger lifts, until a tap outside it; a horizontal drag across a chart moves the crosshair, as the plot only lets the page scroll vertically (`touch-action: pan-y`). Each chart's plot also takes the keyboard focus (its label says how to use it): the arrow keys move the crosshair by a year, Page Up and Page Down by ten, Home and End to the first and last year, Escape hides the tooltip, which is a polite live region so a screen reader reads the values. Both tooltips are placed beside the point in screen pixels and kept inside their frame (`placeTooltip` in `src/app/place.ts`, tested in `test/ui/place.test.ts`), on the side with room, so they are not clipped on a narrow phone, where the charts' svg is scaled down below 280 px.

**The summary** is not a live region, since it is rewritten on every slider move. Instead, a visually hidden status sentence in it, such as "Less warming in 2050: 0.041 °C.", is rewritten 800 ms after the last change, so a screen reader reads it once, when the slider stops.

**Map and Table.** The map card shows its layer in two views of the same data, switched by a pair of tabs with icons, Map and Table, after Our World in Data's charts; the layer, change, gas and food controls above them act on both, and the URL keeps the view under `mapview=table` (left out for the map, the default). The tabs sit at the top right of the card, with the card's Download button beside them, rather than in a row under the view: the table is taller than the map, so a switch under it would move each time the view changes, and at the top it stays under the pointer; up to 760 px wide they take their own row above the controls, still right-aligned. They follow the tab pattern (`role="tablist"`, arrow keys move between them). The note under the view applies to both, the legend only to the map. Its Download button opens the download list between the controls and the view, so the button does not move as the list opens and closes.

**The table** lists every country of the model, not only the largest: country, today, after the shift, the change, and, for production and emissions (and the Change layer of either), the least precise source with its tier and a short link to it; the Data quality layer shows only the country and its source; farmland and forest clearing have no tier. It opens sorted by the column the map colours (after the shift, the change, or the tier), largest first; clicking a column header (a button, with `aria-sort` on the header) sorts by it, names A to Z and numbers largest first, and clicking again reverses it; a country without a value (no change when there was nothing before) comes last either way. A search box filters by name in English or French or by ISO code, ignoring case and accents. The table pages by 20 rows, with Previous and Next and "Page 2 of 10", and says which rows it shows ("Countries 21–40 of 188") in a polite live region. Pages were chosen over infinite scroll: the page under the table stays where it is (the note, the download list and the footer remain reachable), the keyboard and screen readers have a fixed set of rows and controls, and a row's position can be named. The search, a new sort or a new layer go back to page 1; a new layer also goes back to its default sort. On a phone the table scrolls sideways inside its own frame, never the page. The helpers (`tableRows`, `filterRows`, `sortRows`, `nextSort`, `pageOf`) are pure and tested in `test/ui/table.test.ts`.

**Downloads.** The map card's Download button opens a list: the map's layer as CSV (every country with its ISO3 code, English name, layer, measure, gas or food, unit, values before and after, relative change, tier and source; named after the layer and the scenario, such as `planetshift-map-change-emissions-co2e-shift40-2035.csv`); each chart tab's data as CSV, one file per tab (the temperature, 1850–2100, observed, without and with the levers with their 5–95% ranges, and warming from natural factors; the warming avoided, from the current year to 2100; the causes of warming with their ranges and observed temperature under the chosen SSP, then each gas's warming by cause with its range, as `warming_<gas>_<cause>_…`, when the build has it); the scenario as JSON (the full URL state: its address and query, the scenario, the options and the interface's choices, with the summary, the licence, how to cite and the sources from `meta.json`); and the source data files with their sizes (read when the site is built, `__DATA_FILES__` in `vite.config.ts`) and each file's licence. One file per tab was chosen over one wide file because the tabs have different years and quantities. The chart card has its own Download button, at the right of the horizon and years filters just above the chart, that downloads the current tab's CSV; screen readers hear it as "Download this chart's data". A button with nothing to save, as when the model could not compute the scenario, says so beside it. Every entry names its licence with a link: the map's CSV is CC BY 4.0; the chart CSVs and the scenario, which derive from `climate.json`, are CC BY-NC-SA 4.0; the files follow `DATA-LICENCES.md`. A "How to cite" fold gives Planetshift, the page's address and the sources in `meta.json`. The CSV files are a stable machine format, whatever the page's language: UTF-8 with a byte order mark (so Excel reads the accents), comma-separated, CRLF line ends, fields quoted when they hold a comma, quote or line break (RFC 4180), English column names with their unit (`_degC`, `_kg`, or a `unit` column), and plain numbers to seven significant digits with a point for decimals and no thousands separator; a missing value is an empty field. Files are saved through a `Blob` and a temporary link with `download`. The builders are pure and tested in `test/ui/download.test.ts`.

**The deforestation layer** colours each country by the forest area cleared for farming with the shift and the levers, in hectares a year (`deforestationHa`), not relative to anything; its tooltip gives today's clearing, the clearing after, the change, and the CO₂ the clearing releases today and after. A country without clearing is shown with the countries without data ("No clearing or no data"). It reads the deforestation module's `deforestationCo2` and `deforestationChange`, the one place outside a module where the map names a lever's fields.

## Assumptions in the interface

- The current year is the browser's; the temperature chart and the ramp start there.
- The summary's protein and calories are population-weighted world means of the countries in the data, using the base year's population.
- The map's change layer is the relative change once the shift is complete, not in a given year; for land it is the change in cropland and pasture together. The deforestation layer is absolute, also once the shift is complete.
- The land layer shows farmland (cropland and pasture, in hectares) with the shift; its tooltip gives each part before and after, and no emission source.
- The summary's farmland freed is the world total at the full shift, with each part as its change in use (negative when freed) and the total as a share of the world's farmland in the base year; when the shift needs more land than it frees, it says "added". With regrowth on, it adds the CO₂ taken up in the year the shift is complete (`summary.regrowthCo2`), a year, which is already within the CO₂ avoided.
- The data-quality layer and tooltip show, per country, the worst tier among its items under the selected emission scope, with that intensity's source.
- The left panel holds only controls, in groups (see "The Explore page"). There are no ready-made scenarios; the quick 0% / 100% pairs and each lever family's "adopt all in full" and "reset" are the shortcuts. A food set under "Shift each animal food" keeps its own share when the main slider moves.
- Each lever's slider is its adoption, with a one-line description, and each family has "adopt all in full" and "reset". A lever whose data file is missing from the build is disabled and says so; the app still opens, as the loader replaces a missing lever file (HTTP 404) by an empty one.
- The summary's breakdown, "Warming avoided in {year}, by lever group", lists the causes the levers act on, biggest first, each with what the levers avoid of it and, under it, each group's part of it (`causeGroups` in `summaryModel.ts`, from `summary.byFamilyCause`), with bars on one scale coloured by the `--cause-*` tokens of the chart; a group acting on two causes, such as the diet, appears under both, and a part under 0.0005 °C is left out. It is hidden when a single group acts. A part that adds warming is shown as "added" with a hatched bar. The parts add up to the total, and each cause's to the reduction of its band in the Causes of warming chart (see the Levers methodology page for the Shapley values).
- With carbon-in-farmland levers on, the summary adds the CO₂ they store in the year the shift is complete; when forest clearing changes (with the deforestation lever, or with a shift that changes the production of items tied to clearing), it adds the deforestation CO₂ avoided (or added) a year and its share of today's clearing.
- The map's Change layer shows each country's farm emissions with the shift and the levers that act on them (practices, less waste); the change in forest clearing has no matching base in the farm emissions it divides by, so it has its own absolute layer, Deforestation, instead.
- The energy levers change neither the map nor the farm emissions nor the farming band of the Causes of warming chart; they show in the summary (CO₂ avoided, warming avoided and the fossil fuels rows of the breakdown), in the temperature charts and in the fossil fuels band of the Causes of warming chart. With the fossil CO₂ they cut the methane leaked producing the fuel, in the fossil fuels band, and the air pollution burning it made, so the air-pollution band of the Causes of warming chart shrinks after today and the breakdown shows them under air pollution too.
- The *Emissions counted* hint and the summary's note say that wild fish emit only with inputs counted.
- The *AI data centres* option (default: growth added) and the *Permafrost* option (default: left out; a fork can remove it, see "Forking") change the baseline temperature as well as the warming avoided.
- The *World population* option (module `population`, default: the UN's medium projection) is a method option, not a lever: it has no family and no slider, and changes the baseline and the scenario alike through the `population` hook, so the breakdown never credits it. The population chart sits under the temperature chart, with its own axis in billions, the same x range (the range and horizon switches) and the same hover year: hovering either chart shows the crosshair and the values of that year in both (`hoverLink` in `src/chart/frame.ts`). It shows WPP's world total, not the sum of the model's countries, and a note when the projection and the scenario world contradict each other (low with SSP3-7.0, high with SSP1-2.6) or when the SSP2 farm baseline makes the choice moot. With the low or high projection it adds how far that projection moves the baseline at the horizon against the medium one ("With this projection, the warming without the levers in 2100 moves by −0.08 °C from the medium projection's."); the medium projection's baseline comes from `baselineMedian` (`src/model/run.ts`), which reads the run's baseline cache, so it is worked out once per set of options, in about half a millisecond on the real data (`test/model/timing.test.ts`), and never on a slider move. It is hidden when the build has no `population.json`.
- The font is Lato from Google Fonts (`index.html`), with the system font as a fallback; the end-to-end tests ignore a failed font request, so they pass offline.
- Moving a lever slider re-runs the model without redoing the diet shift's production changes (they are cached for the latest diet settings), and the practices' cuts are cached while only the diet moves (keyed once per run by the scope and the practices' adoptions). What depends only on the items or a base vector is computed once and kept beside it: each item's protein and kcal per tonne, its group index and whether it is an animal, the group totals of a country's production, and, for each emission source, the items with a share of it. A run tabulates the baseline's scale over its years once, and less waste reuses the diet's change in food rather than recomputing it. The breakdown's passes without the diet, or without less waste, are kept per set of production groups in play and keyed by what they read, so moving the diet slider does not redo the pass of less waste alone, and moving a lever outside farming redoes none; the other way round, the world parts of the modules outside farming (energy, industry) are kept per set of them acting and keyed by the options, the ramp and their levers, so moving a farming lever redoes none of them. The hot vector code (`util.ts`, `location.ts`, `productionChanges`, the practices' cuts) uses plain loops, which add in item and country order.
